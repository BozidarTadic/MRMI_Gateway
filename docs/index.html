Compliance is Architecture.

MRMI Gateway is federation middleware that enforces cross-border data sovereignty at the transport layer — before your operators can accidentally disable it. Built for messaging. Designed for any regulated domain.

"Legal compliance is not a deployment concern — it is an architectural constraint enforced at the transport layer."
// the problem

A fragmented regulatory landscape

Modern messaging apps operate across jurisdictions with conflicting data localisation rules. Existing federated protocols treat compliance as an implementation concern — leaving operators to figure it out.

152-ФЗ · Russia

Russian Data Localisation

Personal data of Russian citizens must be stored on servers physically located in Russia. Cross-border transmission requires explicit consent and legal basis.

GDPR · EU

General Data Protection

Strict conditions on data transfers outside the EEA. Adequacy decisions, SCCs, and BCRs govern which destinations are permissible at all.

KZ · Kazakhstan

Data Sovereignty Law

Personal data collected from Kazakhstani residents must be processed on local servers. Cross-border flows require regulatory notification and approval.

Existing protocols (Matrix, XMPP) treat compliance as a deployment concern. Operators configure it manually — and can misconfigure it. MRMI Gateway makes the correct behaviour the only behaviour, enforced cryptographically at the transport layer.
// architecture

How it works

Each MRMI node runs a Go binary. Nodes communicate over gRPC with mutual TLS. Every envelope is policy-checked, deduplicated, and appended to a Merkle audit chain. v0.9 adds a Schema Layer that makes the protocol universally adaptable — messaging first, any regulated domain next.

🛡️

Policy Engine

Allow/deny by region, trust tier, and applicable law. Signed TOML — operators can't silently disable it.

🔗

Merkle Audit Log

SHA-256 chained entries. Root hash published to DNS TXT and /.well-known/mrmi-audit for independent verification.

🪪

Identity Trust Tiers

T0 (anonymous) → T3 (legal entity). Trust decays after 30 days without cross-validation. CRL gossip revokes in real time.

📦

At-Least-Once Delivery

Idempotency key + dedup index + ACK/retry. Failed deliveries go to DLQ. Transit cache bridges short outages.

🗂️

Schema Registry NEW v0.9

Domain adapters: messaging, iso20022, hl7fhir, edifact, custom:*. Gateway validates envelope only — payload stays opaque.

🔒

Jurisdiction Isolation NEW v0.9

Per-schema-type tier and jurisdiction restrictions. Financial messages can be locked to regional nodes independent of sender/recipient policy.

// capabilities

Built-in, not bolted on

Every feature serves the core guarantee: regulated cross-border data delivery that operators cannot accidentally misconfigure. Messaging is the primary and current focus — the architecture is ready for more.

🔏

Signed Policy Configs

TOML policy files are cryptographically signed. Fields like applicable_law, allowed_regions, and min_trust_tier are enforced — not advisory.

🌐

Federated Discovery

Hop-limited gossip via BroadcastDiscovery RPC. ExchangePeers keeps the live peer table current. Rate-limited at 10 req/s, burst 20 per origin.

📊

Prometheus Metrics

Counters for allow/deny/duplicate/DLQ depth, transit cache, rate-limit denials, and peer count. Scraped from /metrics.

🔄

Hot Config Reload

File watcher atomically reloads policy without downtime. No restart needed — peers see updated policy within one gossip cycle.

🕵️

Traffic Analysis Resistance

Configurable timing jitter and payload padding per compliance profile. strict applies maximum cover traffic; performance minimises overhead.

🗄️

Pluggable Persistence

NodeStore interface with bbolt (embedded, single-node) and redis (clustered) backends. Audit entries survive restarts.

🛠️

Operator CLI

mrmi node status / peers / dlq / apps — live node inspection. mrmi token issue issues JWT tokens against a running node.

🔗

Webhook Push

HMAC-SHA256 signed push notifications to application webhooks on envelope delivery, policy denial, or CRL update events.

🔒

mTLS Transport

All inter-node gRPC traffic requires mutual TLS. Test certs are generated in-process via internal/testcerts/ — nothing committed, nothing via openssl.

🗂️

Schema Registry v0.9

Declare payload domains via schema_type in the envelope. Built-in adapters for messaging, ISO 20022, HL7/FHIR, and EDIFACT. Custom adapters via TOML. Gateway never inspects the payload.

💸

Financial Corridors v0.2

ISO 20022 adapter with settlement finality, per-corridor cutoff windows, 72h dedup TTL, BIC routing hints, and retain_long audit flag for 7-year log retention.

📜

Protocol Specification v0.9

MRMI is a protocol, not just a Go binary. The envelope contract, policy interface, and audit format are normative — any language may implement a compatible node.

// compliance profiles

Three profiles, one command

Preset configurations map directly to regulatory frameworks. Set profile = in your TOML — the gateway does the rest.

Profile Primary framework Jitter Padding Dedup TTL Transit cache TTL
strict 152-ФЗ / high-risk corridors 100–500 ms Max bucket 300 s 60 s

// quick start

Up in 60 seconds

Prerequisites: Go 1.25+ (protoc only needed to regenerate proto — generated files are committed)

bash
# Clone and run with the balanced compliance profile git clone https://github.com/BozidarTadic/MRMI_Gateway cd MRMI_Gateway go run ./cmd/mrmi-gateway -config configs/node.balanced.toml # Verify the node is healthy curl http://localhost:8080/healthz curl http://localhost:8080/.well-known/mrmi-audit # Run the full test suite go test ./...
STEP 01

Single node

Use configs/node.balanced.toml to spin up a standalone RS node on :8080 (HTTP) and :7777 (gRPC).

STEP 02

Two-node corridor

Follow LOCAL_TWO_NODE_GUIDE.md to run RS + RU nodes locally and test cross-border envelope delivery.

STEP 03

Blazor demo

On Windows: scripts\demo-start.ps1 — starts RS gateway, RU gateway, and the split-screen Blazor UI at :5294.

STEP 04

Seed node

See SEED_NODE_GUIDE.md to join the federated network as a seed node with persistent peer tables.

Strict layered architecture

Dependency flow: cmd/ → internal/app → internal/core → internal/{domain}. Business logic lives only in core — never in transport or HTTP.
